Reviewed: `~/Documents/Claude/LINK` at `0dfba41` plus tonight's working tree (`tests/ref`
re-stamped by the evening's probe run), `src/*` (1,254 lines) and `tests/`. Built on the Mac with
Apple clang `-std=c++14 -O2 -Wall -Wextra -Werror -pedantic -pthread` (clean) and on the Windows

**The verdict in one line.** masm + link.exe ran identically to ml64 + link.exe on all 26

libraries named by full path, 0 of 38 on the next three; and a scratch copy taken through nine
small additions (section C) links all 38 - every one of which then crashes at start-up, because
the import table's terminator lands in the middle of the IAT. What it takes, in the order that
unblocks the most, is section D.

## B. What each leg measured

**B1. masm + link.exe against ml64 + link.exe (26 programs): equivalent, and ran the same.**
Every pair differs by 144-163 bytes: the Rich header (100-117 bytes: masm's objects have no
`@comp.id`, so link.exe writes them as one unmarked entry and the block is 8 or 16 bytes shorter
or longer, moving `e_lfanew` and the whole PE header with it), the reproducible-build stamp in
its three copies (file header, the two debug directory entries' stamps) and the 32-byte hash of
the `/Brepro` debug entry. `.text`, `.rdata`, `.data`, `.pdata`, `.fptable` and `.reloc` are
byte-identical, 05-cc1lab's twelve modules and 13-stats's mixed C/Shalimar included. This is the
same result MASM's own review reached on the objects, now on the images and on the run.

**B2. LINK on RIDE's line (38 programs, 64 applicable legs): 0 linked.**
- `link: libcmt.lib: cannot open` - 51 legs (26 ml64, 25 masm). No `LIB` environment, no
  `/LIBPATH`, no search at all: `slurp` opens the name as given (`layout.cpp:28`). RIDE and the
  compilers' drivers name the CRT by bare name, as link.exe takes it.
- `link: unknown switch /stack:8388608` - 13 legs, every program with a C++ module: cxx1i's
  driver and RIDE add `/stack:8388608`; `main.cpp:59` refuses what it does not know.

**B3. LINK with the libraries by full path and the unknown switches left out (64 legs): 0 linked.**
- `unresolved external symbol: __ImageBase` - 40 legs. The CRT's `exe_main.obj` and friends
  reference `__ImageBase`, which link.exe defines itself (the image base). LINK defines nothing.
- `unresolved external symbol: ?_Xlength_error@std@@YAXPEBD@Z` - 20 legs, every Shalimar
  program. `shmrt-x86_64-windows.lib` is cl-built; its members carry
  `/DEFAULTLIB:"libcpmt"` in `.drectve` (18 of them) and link.exe pulls `libcpmt.lib` on that
  word. LINK drops `.drectve` (`coff.cpp:52`, LNK_INFO) unread.
- `libcmt.lib(): machine 0x0000, not x86-64` - 4 legs (16-hd-standard-headers, 21-hd-setjmp).
  libcmt.lib has 130 members with machine 0 (`almap\*.obj`: one section, five symbols, one weak
  external each - `_setjmp -> __intrinsic_setjmp`, `time -> _time32`, `_tcsupr -> _mbsupr`...).
  link.exe takes machine 0 as "any"; `coff.cpp:60` refuses it. The member's name in the message
  is empty because `Archive::member` names a member by its 16-byte field, which is `/123` here
  (long names live in the `//` member, which the reader does not consult).

What the 38 crashing images look like against the oracle (01-hello: 494,080 bytes against
111,104; 06-smart 495,104 against 143,360):
- **the IAT terminator is in the middle.** kernel32.lib's `KERNEL32_NULL_THUNK_DATA` member
  contributes the zero words that end `.idata$4` and `.idata$5`; it is pulled in the first pass
  (the first import pulls `__IMPORT_DESCRIPTOR_KERNEL32`, which references it), and later passes
  pull more imports after it. Contributions of one name are ordered by module serial, so the
  zero lands where the pull put it: hello's IAT has 93 words with the zero at position 72, the
  oracle's 77 words with the zero at 76. Every import after position 72 goes through a slot the
  loader never filled. That alone explains the 38 crashes.
- `.pdata` is not sorted: 1,815 RUNTIME_FUNCTIONs, 713 out of order (oracle: 344, 0 out of order).
  The unwinder searches it by bisection.
- no COMDAT selection: every `.text$mn` from every pulled member is placed, definition or not,
  so the image is 4.4 times the oracle and carries 5.3 times its function table.
- 13 output sections against the oracle's 6 (`.text .rdata .data .pdata .fptable .reloc`): the
  CRT's `.00cfg`, `.gehcont`, `.gfids`, `.rtc`, `_RDATA`, `_guard_check_icall_$fo_bdd$`,
  `_guard_dispatch_icall_$fo_bdd$`, `memcpy_$fo_bdd$` each became a section (`out_of` keeps any
  name it does not know); link.exe merges `_RDATA` and `.rtc$*` into `.rdata` and `.data` and
  drops the guard/CFG tables when `/guard:cf` is off.
- no load-config directory (the oracle's is 0x140 bytes, from libcmt's `_load_config_used`).

bytes (the Rich header counting the scratch's own modules), so the import path's shape is close
once the section-class symbols resolve; p03 and p09 (106 and 385 bytes) are the ILT/IAT order

**B6. What the three new probes settled (`tests/ref`, run tonight on the box).**
- **p09-twodll** (kernel32 + user32, five names each, referenced GetDesktopWindow, IsWindow,
  GetStdHandle, WriteFile, ExitProcess, GetLastError, Sleep, CharUpperA, GetKeyState,
  MessageBeep; ran, rc=1 as written): the IAT is one run at 0x2000 - kernel32's five words and
  a zero, then user32's five and a zero (directory size 0x60); the two descriptors and the null
  one follow at 0x216C, kernel32 first (first library on the line); the two ILTs at 0x21A8 and
  0x21D8; the hint/name blobs after. kernel32's order is WriteFile, ExitProcess, GetLastError,
  Sleep, GetStdHandle - the first-referenced name last, exactly as p03 showed - while user32's
  is the reference order, GetDesktopWindow first. The object's symbol table has both DLLs' names
  in reference order (symbols 10-19). So "first referenced goes last" holds for the first
  library and not the second; the rule is still not read, but it is now two points, not one.
- **p10-rich-odd** (an ml64 object, a masm object with no `@comp.id`, no imports): three Rich
  entries, in the order 0x0103899C (ml64) ×1, **0x00000000** ×1, 0x0102899C (link) ×1. Two
  things `pe-observed.md` had wrong: an *object* without `@comp.id` counts as 0x00000000, and
  only a short import member counts as 0x00010000 (LINK uses 0x00010000 for both,
  `coff.cpp:66`); and "ascending, then adjacent pairs swapped" does not produce this order
  (ascending gives 0x0, 0x0102899C, 0x0103899C; the swap gives 0x0102899C, 0x0, 0x0103899C).
  LINK's image differs by 127 bytes here.
- **p11-stack** (`/stack:8388608` on the bare program): SizeOfStackReserve 0x800000,
  SizeOfStackCommit unchanged at 0x1000; nothing else moves. LINK refuses the switch.

**B8. The claims the README makes.** One thread per input file: true of the command-line inputs

diagnostic at the point of interception: true, with the two lapses above.

### Not the linker's fault - found on the way, not edited (reported to the caller)

- ml64 refuses cxx1i's x86_64-windows output (`A2008 syntax error : COMDAT`, line 41 of

  ml64 legs are therefore not applicable to 12 programs; masm + link.exe is their oracle.
- **link.exe's own images from masm's C++ objects have out-of-order `.pdata` entries** - 06-smart
  1 of 419, 07-vector3 7, 08-cxx1lab 11, 14-mixed 7, 23 1, 25-include-streams 12, 26 1, 29 1 -
  where every ml64-object image has none. The misplaced entries are the ones whose unwind info
  sits lowest in `.rdata` (smart: `??0Counter@demo@@QEAA@H@Z` at RVA 0x1390, unwind at 0x20000,
  filed after the entry for 0x1611D). link.exe sorts `.pdata` for cl's and ml64's objects; that it
  did not here points at something in how masm writes the ASSOCIATIVE `.pdata` COMDATs. The
  programs ran correctly, so no exception was unwound through those functions; one that is
  would find `RtlLookupFunctionEntry` missing them. Worth a MASM probe.
- cxx1i refuses `throw std::runtime_error(...)` for x86_64-windows ("only a fundamental type has
  a type descriptor this compiler can name") and "a local with a destructor and a `try` in one
  function" - 14-mixed was rewritten around both. 31 of 330 cxx1i cases refuse x86_64-windows;
  2 (`dtor-throws-unwinding`, `noexcept-local-terminates`) call POSIX `close` and cannot link on
  Windows with any linker.
